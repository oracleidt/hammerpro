# BSP Sniffer

The BSP Sniffer joins a Garry's Mod server and recovers the map exactly as the game loaded it, then writes a VMF you can open in Hammer Pro, the recovered BSP, and the content of the map (models, materials, sounds, pakfile). The map is rebuilt from the memory of the running game: it never needs the map file. A map protected with [Protect your BSP](bsp-protection.md) is recovered too: the engine has to load the map to draw it, so the sniffer reads what the engine loaded and restores what the protector scrambled. You type an `ip:port`, click **Sniff**, and Hammer Pro does the rest: it starts Garry's Mod through Steam, joins the server, waits for the map to load, reads the game memory, rebuilds the map, decompiles it and closes the game.

**It works only for Garry's Mod.** It was tested with the x86-64 branch of Garry's Mod (build 2026.09.17, Steam build 26229091) on Windows, and with the 32 bit executable of the same install. Other Source games and other builds are not supported.

## Authorized use only

Only use the BSP Sniffer on servers and maps you are authorized to test. You are responsible for what you do with it. The Hammer Pro authors are not responsible for how it is used, or for any consequence for your accounts, servers or maps.

The first time you open the panel a warning dialog asks you to confirm that you understood. The warning stays visible in the panel, and **Sniff** stays disabled until you tick **I am authorized to test this server and map**.

On a VAC secured server the game runs with VAC while Hammer Pro reads its memory. Hammer Pro only reads (it never writes, injects or hooks anything), but a server or a community that forbids this kind of tool may sanction you. Hammer Pro asks the server first and adds `-insecure` only when the server is not VAC secured (setting **-insecure**, automatic by default): a VAC secured server refuses an insecure game.

## Opening it

**File > BSP Sniffer...** (action `bsp_sniffer`) opens the panel. **File > BSP Decompiler...** is the other tool: it decompiles a `.bsp` file you already have.

## Local game and running game

A second Garry's Mod cannot join your own server on the same computer (Steam allows one game), so the sniffer has two equivalents that give the client memory of a real join:

- **`map:<name>` as the server**: Hammer Pro starts Garry's Mod with `-insecure +sv_lan 1 +maxplayers 2 +map <name>`, waits for the console to report `Map: <name>`, reads the memory and closes the game. The map file must be in `garrysmod/maps` (or where the game finds it), exactly where a downloaded map ends up. The server query is skipped.
- **`map:` alone with *Use Garry's Mod if it is already running***: reads the game that is already running with a map loaded (singleplayer, listen server or a server joined by you). The map name is taken from the console log. Hammer Pro never closes a game it did not start. Turn **Disconnect from the server when done** off in this mode: disconnecting unloads the map and leaves stale data in the memory.

## Settings

There is no map file to configure by default: the whole map is rebuilt from the memory of the game, and no map file is opened. Every lump comes from the structures the engine keeps once the map is loaded (see [What the memory gives](#what-the-memory-gives)). The option **Also use the map file of the client** (`use_map_file`) is off. When you turn it on, the file the client has (game cache `map_pack.bsp`, `maps`, `download`, addons, workshop archives) is read through its lump directory, so a protected file with shuffled lumps, gaps, decoy blocks, a scrambled header or a pakfile anywhere is read like any other. It is used only when it matches the memory (same entities, same verified lumps), every field taken from it is checked against the memory first, and a file that is altered or different is ignored.

## How it works

1. **Preflight.** The server is asked with the Source query protocol (map, players, VAC). Garry's Mod is detected (64 bit and 32 bit branches).
2. **Launch.** Steam starts the game with your launch options, `-condebug` and `+connect ip:port`. Hammer Pro finds the game process by its image path, so Steam helper processes are ignored.
3. **Wait.** The console log tells when the connection is made and which map is loaded. The sniffer then scans the memory of the game for the entity lump of the map (the `worldspawn` entity and its siblings). The menu background map that is always loaded first is ignored, and the map must stay identical for the settle time. The entity lump is in memory well before the engine has finished building the map, so the sniffer keeps reading until the engine has built every displacement (the face records carry a displacement flag, which gives the expected count), every overlay has its faces, the static props are all resolved, and two consecutive scans give identical counts. This wait is bounded by **Wait for the map**; a slow server can take several minutes.
4. **Capture.** Everything below is decoded from the memory of the game, with no file involved:
   - the engine world structure: the block of counts and pointers the model loader fills (planes, leaves, nodes, faces in four parallel arrays, texture infos and data, vertexes, vertex indices, lightmap data, world lights, ambient lighting, vertex normals, primitives, area portals, cubemaps, occluders, displacement objects, ...). It is found from its plane array (never by a fixed address), told apart in its 64 bit and 32 bit layouts, cross checked against the collision data, and every array of it that cannot be read is listed in the report as not recognised. The collision structure (brushes, sides, boxes, nodes, leaves, models, visibility) is found the same way, from the entity text it points to;
   - the entity lump, with every keyvalue and every output;
   - the entities the server networks to the client: the client entity list, found from the type information of the game, with the offsets of the network tables, merged with the lump (see [Entities of the client](#entities-of-the-client));
   - the collision data (brushes, brush sides, axis aligned boxes, planes, nodes, leafs, models, and the material of every side);
   - the render data: the face records (plane, side, vertex indices, texture info, displacement object), the vertex array and the vertex index array, and the texture info records (88 bytes: the two texture axes, the lightmap axes, flags and the material). The texture info of a material is told by the order of the material objects, which follows the order of the collision surface names;
   - the displacements: the engine keeps, for every displacement, its start position, its power and the final position of every vertex. The sniffer rebuilds the flat grid of the face and turns the offset of every vertex into the direction and distance stored in a BSP; the triangle tags are recomputed from the slopes. The blend painting (vertex alpha) and the allowed vertex bitmask of every displacement are read from the same displacement object (a 10 word bitmask right after the start position) and from the engine's own vertex buffer, matched to the rebuilt positions by their coordinates;
   - the static props: the engine keeps one object per prop (model, origin, angles, skin, solidity, leaf range, the index in the compiled list, bounds, an explicit lighting origin when the map set one); the list is found as a run of equal sized objects whose model names resolve to `.mdl` files. The fade distances are read from a second table (found by its own record shape and matched to the props by their index, whether the engine stored them as plain or squared distances). The flag byte of the object carries the fade, no draw, screen space fade and no per vertex lighting bits exactly as the compiled map has them, and the use of an explicit lighting origin is read from the lighting origin itself (the engine stores the centre of the bounds when the map set none);
   - the overlays: the engine keeps the table with the texture info, the faces, the UV extents and the origin and basis of every overlay; the render order rides in the same word as the texture info (its top two bits);
   - the cubemaps: the names of the cubemap textures, `maps/<map>/c<x>_<y>_<z>`, carry the origin of every `env_cubemap`; their sizes are read from the engine's own cubemap sample table (origin, a pointer to the loaded texture, and the size), matched to the names by origin;
   - the occluders: found as a chain of fixed size records (bounds, polygon range) followed, at a small search distance, by the polygon table and the vertex index table, every polygon and every vertex checked against the recovered planes and vertexes before being accepted;
   - the area portals and their vertices: found as a chain of records whose vertices lie on the portal planes;
   - when a map file is allowed and found, a cross check: the lumps the engine keeps as they are (planes, vertexes, visibility, leaf brushes, areaportals, lighting, ambient lighting, vertex normals, texture names...) are compared byte for byte, the collision data brush by brush, and the counts of everything are compared in the report.
5. **Fill in (optional).** Only with **Also use the map file of the client** on. A map file that matched the memory (the same entities, lumps confirmed byte for byte) fills in, record by record, what the engine still does not keep by itself (the few fields below), and cross checks what it decoded from memory everywhere else. Each record is validated against the memory first and ignored when it disagrees:
   - the displacement triangle tags, when a matching file disagrees with the ones computed from the slopes (rare, and only for a tag the slopes could not decide);
   - the solidity of the static props, and the three flag bits that exist only for the compiler: ignore normals, no shadow and no self shadowing (see Limits);
   - the texture axes of the brush sides that no rendered face covers (matched by brush and plane, and only when the texture axes equal the ones in memory);
   - the pakfile of the map, when the rest of it (textures, strip and physics files) is wanted: only the `.mdl` of a model is whole enough in the engine's own memory to be rebuilt without the file (see Limits).
   The report lists, for every category, its source: memory, map file, game content or absent.
6. **Rebuild.** A valid BSP is assembled from what was decoded and filled in: the brush table, brush sides, planes, nodes, leafs, models, faces, edges, vertexes, texture info and texture data, displacement info, vertices and triangle tags, overlays, cubemaps, area portals, the static props as a game lump and the pakfile. Each brush side takes the texture axes of the rendered face that lies on its plane and inside its brush (the largest overlap wins); a side that no face covers, because it is hidden inside other brushes, gets the axes of the file when there is one, else world aligned axes. When the game memory has no render data and a file exists, the map file is used instead.
7. **Decompile.** The BSP goes through the same decompiler as **File > BSP Decompiler...**, with your switches.
8. **Content.** The game content (downloaded workshop addons, addons, the server downloads) is searched for the models, materials, sounds and particles the VMF uses. The pakfile of the map exists only in the map file: it is extracted when a map file is allowed, found and matching. Without it, the model files of every model that the game loaded and that is not on this computer are rebuilt from the memory of the game: the `.mdl` (whole in the model cache), the `.vvd` (resident in the model cache in its own file layout), the `.dx90.vtx` (rebuilt from the hardware mesh groups the renderer keeps) and the `.phy` (rebuilt from the collision data of the model cache); the materials the engine loaded and that are not on this computer are rebuilt as `.vmt` text, with their proxies. The textures stay in video memory and are listed with the measured residency (see Limits). The game also holds the directory of the pakfile (every file name with its size and CRC32); it is listed in `pakfile_listing.txt` and every file in the content folder is checked against it, so a rebuilt file is reported identical or different with no map file at all (on the test map: 609 entries, the `.dx90.vtx` and `.phy` of the custom model identical, the `.mdl` and `.vvd` different as described below). Files that exist in the base game are skipped when **Only content that is not in the stock game** is on. The reflectivity of each texture data entry is corrected with `$reflectivity` of the `.vmt` of the game content, or failing that with the header of the base texture (the log gives the number of values replaced).
9. **Finish.** The game is closed by its own process id (and its helper processes). Nothing else is ever closed.

Memory is read with `ReadProcessMemory` after enabling `SeDebugPrivilege` when allowed; the 64 bit game needs the 64 bit Hammer Pro. The game is only read, never modified.

## Protected maps

[Protect your BSP](bsp-protection.md) ships a copy of the map that drops the logic entities and every input and output, empties the original faces lump, scrambles the material names (`hp/xxxxxxxx`, with a patch material that includes the real one), watermarks the world entity and can add a server lock. The game still loads and draws that copy, so the sniffer reads the same data as for any map and then undoes what it can:

| What the protector does | What the sniffer recovers |
| --- | --- |
| Scrambled material names (`hp/` plus eight hexadecimal digits) | The loaded material objects keep the reflectivity of their texture; the sniffer indexes the texture headers of the game content (cached in the sniffer folder, a few minutes the first time) and names the material after the texture with the same reflectivity. A reflectivity shared by more than four textures is not used. A guess can be wrong when two materials share a texture, and the report counts guessed names apart. No map file is involved: the names come from the game memory and the game content only. |
| Custom materials and textures renamed (`hp/` files in the pakfile) | They are kept with their scrambled name, and the files are saved in the content under that name, so the VMF still renders. The original name was replaced by a hash with a random salt that is not in the map: it cannot be recovered. |
| Entities removed that the server still sends to the client (`weapon_*`, `item_*`, `npc_*`, props...) | Added back from the networked entities of the client (see [Entities of the client](#entities-of-the-client)): class name, `origin`, `angles`, `model`, `spawnflags`, render fields, `skin`, `body`, `modelscale`. The position is the one of the capture. |
| `parentname` removed | Restored when the parent is a networked entity whose name is in the entity lump. |
| Brush entity removed (a brush model that no entity uses) | The brush model becomes a brush entity again: `trigger_multiple` for trigger texture brushes, `func_brush` otherwise, with the origin stored in the model. |
| Logic (`logic_*`, `math_*`, `filter_*`, `game_*`, `ai_*`, `point_*`...), `info_node`, `path_*` and every input and output removed, `hammerid` and comments removed | Not recoverable: the server never sends them and no copy exists in the memory of the client (measured, see [Entities of the client](#entities-of-the-client)). Every entity the protector kept is complete. |
| Original faces lump emptied | The engine does not use it. A brush side that no rendered face covers takes the texture info of the same material that fits its plane (see Limits), or the one of the brush side record of the map file when the map file is allowed. A very small number of sides whose texture came from the original faces keep the texture of the brush side record. |
| Watermark and server lock keys on the world entity | Read, shown in the report and removed from the VMF. |

The report has a line `protected map` and a row `material names of a protected map` in the table of sources with the numbers of each case.


## What the memory gives

Once a map is loaded the engine keeps almost every lump in its own structures, so no map file is needed. The sniffer rebuilds the lump bytes from them. The real map files were used only as ground truth in the tests that measured the table below (`gm_construct`, the 155 MB workshop map `union_blue_lock_v2`, and twelve protected variants of `gm_construct`), never by the sniffer. "Identical" means byte for byte.

| Lump | Where it comes from | Measured |
| --- | --- | --- |
| planes, vertexes, nodes, models, leaf brushes, brushes | the arrays of the collision and render structures | identical on both maps |
| leafs | the leaf array (bounds from the centre and half size, area and flags, cluster, water, face range) plus the collision brush ranges; a solid leaf without faces starts at 0 | identical on both maps |
| leaf faces | the mark surface pointers turned into face indices | identical |
| visibility | the visibility block of the collision world | identical (116293 and 3995877 bytes) |
| lighting and HDR lighting | the lightmap block, whose length follows from the face records | identical, 12274916 and 60546524 bytes, both sets (the second one from the second reading) |
| leaf ambient lighting and its index | the ambient arrays | lighting identical; the index identical for every leaf that has samples. For a leaf without samples (3185 of the 5002 leaves of `gm_construct`) the "first sample" field is the running counter of the compiler at the moment one of its threads handled that leaf: the engine does not use it (the sample count is zero) and no structure keeps it, so it cannot be recovered |
| world lights and HDR world lights | the world light array; the radius the engine computes for lights that have none is cleared again | identical on both maps |
| faces and HDR faces | the four surface arrays: plane, side, node flag, first edge, edge count, texture info, styles, light offset, lightmap mins and size, primitives | every field identical except the face area, the original face and the smoothing groups (not kept). The area is recomputed: even starting from the vertices of the compiled file itself, the best formula tried (fan in single or double precision, sum of cross products, shoelace) gives the exact float for only 73.8 percent of the faces of `gm_construct` (6899 of 9350) and 95.7 percent of those of `union_blue_lock_v2` (42278 of 44169), because the compiler computes the area on a polygon that still had vertices the emission merged afterwards |
| texture info | the texture info array | identical on `gm_construct`; the texture data index comes from the material order and the brush sides (see Limits) |
| texture data | names and name table from the surface array; reflectivity from the material objects; size from the texture objects | strings and table identical; the reflectivity is the one of the material object, replaced by `$reflectivity` of the `.vmt` of the game content when it has one (the engine keeps only the one of the texture): 203 of 204 on `gm_construct` (201 before the `.vmt` files were read; `TOOLS/TOOLSHINT` stays at 0.332 in its texture header as in memory, while the file says 0.361); size 203 of 204 (the water texture of the map, loaded at 256 instead of 128) |
| physics collide | the solids of every model (header rebuilt, the markers the engine writes into them cleared) and the packed key values decoded back to their text | all key texts identical; 3109795 of 3109804 bytes identical on `gm_construct` (the 9 others are mark counters that the engine writes into nodes of two solids and that recent compilers already write into the file: the two cases cannot be told apart in memory, only the mark of the root, which is the runtime one, is cleared); 6474856 of 6474871 bytes on the workshop map, whose 15 differences are the last digit of the volume of a solid (`83375.007813` in memory, `83375.007812` in the file: the compiler text comes from a double, the float in memory does not say on which side of the half it was) |
| displacement info | the engine's displacement objects: start, power, contents, neighbours, allowed vertices, lightmap start | every field identical except: the start position of 23 of 110 displacements (`gm_construct`) and 17 of 211 (workshop map), which the engine aligns on a vertex of the face (up to 0.054 unit apart) while the compiler writes the original value; and the 2 padding bytes of the record, which are uninitialised heap bytes in the file (non zero in 37 of 211 records of the workshop map). The contents come from the second record the engine keeps per displacement (an array of 352 byte records, found by the start positions) and no longer from the main object, which only keeps a plain solid flag: identical for 211 of 211 |
| displacement lightmap sample positions | the vector the displacement loader keeps | identical |
| vertex normals and their indices, primitives and their indices, leaf water data, leaf minimum distance to water, areas, area portals, clip portal vertices, cubemaps with their sizes, occlusion | the corresponding arrays | identical on both maps (occlusion of the workshop map: 16424 bytes) |
| map flags | the booleans the engine derives from the lump, found by a code signature in the engine module | identical (3 and 0); bit 0 is inferred, because the engine folds it into bit 1 |
| overlay fades | the overlay record of the engine (squared fade distances) | identical: -1 and 0 by default on `gm_construct` and the workshop map, and 40000 / 640000 then -1 / 90000 on a test map with two fades set |
| face macro texture indices | not kept by the engine | 0xffff for every face is assumed: identical on the 4 tested maps that have this lump (all 0xffff), the workshop map has none |
| edges and surface edges | rebuilt from the vertex index array | equivalent, not identical: the arrays of the compiler also hold the edges of the original faces, which the engine never loads (20749 of the 65623 surface edge entries of `gm_construct`, 31.6 percent), so the numbering cannot be redone from the displayed faces alone |
| entities | the entity text | identical to what the client received |

Not in the engine memory, measured: the original faces (27), the face ids (11), the smoothing groups and the original face index of a face, the face macro texture info (47, assumed all 0xffff). No 24 byte window of the first two was found in a snapshot of the whole game process, and no field of the surface arrays follows the smoothing groups. Everything else of the list at the top of this page is read from memory.

On `gm_construct` 75.1 percent of the bytes of all lumps (27,6 of 36.7 MB) are whole lumps identical with no file, and 87.5 percent of the bytes are identical at their position when the nearly identical lumps are counted (physics: 3109795 of 3109804 bytes); on the workshop map 88.7 percent (137,9 of 155.5 MB) and 97.2 percent; 75.1 percent (27.4 of 36.4 MB) on eleven of the twelve protected variants, 74.9 percent on the twelfth, compared with the protected file the game loaded, and 87.7 percent of the bytes at their position. A whole lump only counts as identical when it is identical to the byte: the 9 mark bytes of the physics of `gm_construct` alone remove 3.1 MB from the first measure. The remainder is the pakfile, the lumps listed above that the engine does not keep, the static props game lump and what is equivalent but not identical.

## Entities of the client

A normal join gives the client two sources of entities, and the sniffer reads both:

- **The entity lump of the map**: the file the client downloaded, parsed by the engine. It holds every entity of the file with every key value and, when the file was not protected, every input and output.
- **The networked entities**: the entities the server keeps sending to the client (props, brush entities, weapons, items, npcs, env entities...). They live in the client entity list with the fields the server sends for them.

The networked entities are read from the game memory without any hard coded address: the list object and every entity object are found from the type information of the game (RTTI), and the offset of each field comes from the network tables of the game (`DT_BaseEntity`, `DT_BaseAnimating`), so a game update that moves a field is followed. The sniffer then merges them with the lump:

- every entity created by the map carries its **map creation id**, its position in the original entity lump (the world entity has the base id). The id survives the protector: it tells which entities of the original lump are missing from the shipped file;
- the **real class name** of a networked entity is read from the class name string table that the game keeps, its model from the model string table (the table of the loaded map is recognised by the world entity: its class must be `worldspawn` and its model the map file);
- a networked entity that the lump already holds (same class name, same model, same position or same place in the original lump) is matched to it, and gives back its `parentname`, a key the protector removes, when its parent is a networked entity with a name;
- a networked entity that the lump does not hold is **added** with its class name, `origin`, `angles`, `model`, `spawnflags`, `rendermode`, `renderfx`, `rendercolor`, `renderamt`, `skin`, `body`, `modelscale` and `parentname`. These are the values the server sends now: a prop that fell has the position where it lies;
- a brush model of the map that no entity uses (the entity was removed with its inputs and outputs) becomes a brush entity again in the decompiler: `trigger_multiple` when every side has the trigger texture, `func_brush` otherwise, with the origin stored in the model.

The report has a line `client entities` with the numbers, the entities added by class name, and the lower bound of what is missing: the highest map creation id minus the entities of the lump and the added ones.

What the client does not hold, and why:

- The server sends an entity to a client only while it is in the view of the player (or flagged as always sent). An entity that was never sent has no object on the client. The sniffer cannot move the player: it only reads.
- Logic (`logic_*`, `math_*`, `filter_*`, `game_*`, `ai_*`, `point_*`...), `info_node`, `path_*` and every input and output of an entity are not networked at all. They exist only in the memory of the server and in the full map file of the server owner.
- `hammerid`, comments and the names of removed entities are never sent.
- A **remote** dedicated server is therefore recovered to exactly what the client holds: the lump as shipped, the networked entities, the brush models. A local listen server (`map:<name>`) is only a test aid: the sniffer reads the client side structures only, never the server side entities of the same process, so the result is the same as a remote join.

Measured on `gm_construct` with 20 test entities added (weapons, items, npcs, brush triggers, logic, a template, a prop with outputs...). The full map was loaded in a local listen server only as a test aid; the sniffer read the client structures only and merged them with the entity lump of the protected file (the same input as a remote join with a protected file). Unprotected map: 1247 of 1247 entities, every key value (9087 of 9087) and 32 of 32 outputs, nothing added twice. Protected with every option of [Protect your BSP](bsp-protection.md): the original lump has 1247 entities and the shipped file 391 (856 removed: 815 `info_node`, 22 `path_track` and `path_corner`, 19 other entities). The client gave back 9 of the 9 removed entities that the server networks (2 `weapon_smg1`, 1 `weapon_pistol`, 2 `item_healthkit`, 2 `item_battery`, 2 `npc_headcrab`, near the spawn and 3000 units away) and none of the 847 others; every one of the 391 kept entities was matched, and the lower bound computed from the map creation ids (847) is exactly the number of entities that stay lost. The inputs and outputs of the removed entities (31) and all `hammerid` keys stay lost. No copy exists in the game memory: a search of the whole process (1190 MB: heap, mapped memory and module images, ASCII and UTF-16) for 15 strings that only exist in the removed entities (target names, a comment, output parameters, hammer ids) finds 2 to 19 hits each in the heap after loading the unprotected map, and no hit at all for 9 of them after loading the protected map (the target names, the comment, the template and hammer id strings); the 6 that remain are strings the game itself contains (`SetTrack` and `PickRandom` are input names of the engine, `HeliPathLuaHook` is in a Lua file, `crab1`, `wsmg` and `900001` are short chance matches).

## Limits

- Garry's Mod only, Windows only.
- Hammer Pro reads the memory structures of the x86-64 build 2026.09.17 of Garry's Mod and of its 32 bit executable shipped in the same install (`bin\gmod.exe`), selected with **Game version**. On the 32 bit game the engine world structure, the collision world, the lighting, the displacements and the physics are read and verified like on the 64 bit one (83.5 percent identical bytes on `gm_construct`, the same lumps as the 64 bit run); the static props (182 of 182), the overlays (11 of 11, with their fades), the cubemaps, the area portals, the displacement vertex alphas and the displacement contents are read too, with their own 32 bit record sizes and offsets (`LAYOUT_X86` in `engine.rs`, measured in a snapshot of the 32 bit game); the rebuilt BSP of `gm_construct` is identical, lump by lump, to the one of the 64 bit run (27595979 bytes of whole identical lumps in both cases). The older 32 bit main branch build was not installed (downloading it needs a Steam login of an account that owns the game, which a tool must not type, and putting it in the current install would replace the 64 bit beta; in a separate folder, `steamcmd +force_install_dir <folder> +login <account> +app_update 4000 -beta <branch>` and then that folder in **Garry's Mod folder**); what it needs is a run on it with the same probe, because only its record sizes and offsets can differ, and `Profile` in `hubdec.rs` is where they are. On another build the report lists which structure was not recognised: the world structure is checked against the collision data, and the leaf, node and face layouts against each other. Tested by changing the record size of a leaf, a node or a face by 8 bytes on purpose (example `forced`, on a snapshot of `gm_construct`): every time the report names the structure and the record size that no longer passes the checks ("the leaf records (96 bytes each) do not agree with the collision leaves", "the node records (104 bytes each) do not pass the plausibility checks", "the face records (48 bytes each) do not pass the plausibility checks") and lists the missing lumps.
- Everything that used to be listed below as "not kept by the engine" (displacement vertex alphas and allowed vertices, static prop fade distances, cubemap sizes, overlay render order, occluders) is now read from the game memory itself; a map file is only used as a last resort when one of these cannot be found there (for example a 32 bit game, see above). What the engine genuinely does not mirror one for one is smaller now:
  - of the 8 flag bits of a static prop, 5 come from the game memory and matched the compiled map on 182 of 182 props of each of two test maps with different random flags: fades, no draw, screen space fade, no per vertex lighting, and the use of a custom lighting origin (read from the lighting origin itself). The other 3 (ignore normals, no shadow, no self shadowing) are used only by the compiler: when it creates the prop object the engine masks the flag byte of the lump with 0x65 and tests bit 2 once, and never reads these bits again (checked in the machine code of `engine.dll` at the function that creates the object, and by searching the whole process for any array or bit field that follows them, packed or not: none exists; 59, 52 and 46 of the 182 props of the first test map and 80, 84 and 71 of the second had these bits). They are taken from a matching map file when one is allowed and found, and left at their default (off) otherwise;
  - the triangle tags of a displacement are recomputed from its slopes; on every tested map this matches the compiled tags, but a tag the slopes leave ambiguous is taken from a matching file when one is allowed;
  - the texture axes of brush sides that no face covers (hidden inside other brushes) are not in the engine: such a side takes the texture info of the same material whose axes lie in its plane (59 percent of the hidden sides of `gm_construct` get exactly the compiled texture info), else a world aligned one; with a matching map file (when allowed) they are taken from it;
  - pakfile content beyond the `.mdl` of a model: the model file itself is whole enough in the engine's model cache to be rebuilt without a map file (a 7980 byte custom model came back with 2 bytes different, both engine side runtime patches, LOD count and a padding byte). The other files are rebuilt from the structures of the model cache and the material system:
    - vertex files (.vvd): the vertex file stays resident in the model cache in its own file layout (header, fixups, vertices, tangents) and is found by its header and checksum. On the 950 models with geometry of a live test map: 760 identical to the real files, 165 identical after the engine cut the LODs below the root LOD (only the vertices the engine kept, so a game attached while running should have started with `+r_rootlod 0`, which Hammer Pro does itself), 17 with no resident vertex file (animation only models, or models the engine unloaded from its cache since), and 8 different: 2 partial because the engine freed the block and reused its memory (136 of 378 and 3693 of 4840 vertices lost; none of the lost positions exists anywhere else in the process, 0 of 248 checked on the three worst cases of a first run), and 6 whose vertices are the same set as the file found on this computer in another order, which means the game loaded another compile of the model. When the engine applies the fixups of a model it drops the table: the rebuilt file then keeps the vertices in their final order with no fixups, which is valid but not byte identical (the custom model came back with the same 573 vertices and tangents);
    - strip files (.vtx): rebuilt from the hardware mesh groups the model cache keeps for the renderer: the strips with their bone state changes, the group to mesh vertex map, the indices, the flags, the LOD switch distances and the material replacements (the vertex bone numbers come from the `.vvd`). The custom model came back byte identical (15518 bytes, and its checksum equals the one of the pakfile directory). On 907 stock models of the live test map every group, strip, vertex, index and state change equals the real file; 698 files are byte identical and the other 209 differ only in the unused bone slots of the vertices (0 or 255 depending on the era of the compiler that wrote the real file; the rebuilt file uses 255 for a model written by the current compiler and 0 for an older one). The dx90 variant is rebuilt (the game loads it first) and a dx80 or sw file that the pakfile lists gets a copy of it;
    - physics files (.phy): rebuilt from the collision solids and the packed key values of the model cache; the key tables of every block (solid, fluid, ragdollconstraint, animatedfriction, collisionrules, staticsolid) are read from `vphysics.dll` and the engine's own rounding of the numbers is followed. In the live test 847 collision sets were loaded: 617 are byte identical and 230 identical except letter case (the physics library lowercases names; the case is restored from the strings of the `.mdl` when it holds them). A model whose physics were never created in the game has no collision data in memory: 182 such models were checked, 1 of their 2586 solids exists anywhere in the process;
    - material text (.vmt): rebuilt from the key values when the engine kept them, else from the material variables and the proxy objects of the material (the class of a proxy comes from its run time type information, and the member layout of 64 proxy classes was read from their constructors in `client.dll`; every stock proxy of the 767 stock materials compared matched the real file). A patch is rebuilt resolved (the final shader with the merged values), a conditional block keeps the branch the engine chose, and a value the shader derived itself is left out. Proxies written in Lua (`PlayerColor` and the like) get their parameters from the Lua state: the values table the game passed to the script is found through the registry key the proxy object holds (the proxy name followed by the material name), and all 14 Lua proxy parameters of the stock materials compared matched the real files;
    - textures (.vtf): the pixels are in video memory only. Measured with a random 256 by 256 texture added to the pakfile of a test map: none of its data exists in the process, in any channel order (0 of the sampled windows in the original order and in four swizzled orders). Of 572 textures that have a file on this computer, 44 have the whole file resident (read by the file system and kept), 55 partly, and the others nothing; none of the 140 textures missing from this computer has a resident copy of the same size and format that could be theirs (6 have a resident file of the same size and format, each listed; for the random control texture it was checked not to be its copy). `textures_in_video_memory.txt` gives the size, format and that count for every missing texture, and `texture_residency.txt` the measured residency of the others. Reading the video memory itself would need calling the Direct3D device of the game or injecting code, which Hammer Pro never does, so these files stay listed as missing.
- Lighting: the game loads one lighting set, so the other one needs a second reading: the game is switched to LDR (`+mat_hdr_level 0`) and the map is loaded again in the same process (`+map` for a local game, `+retry` and then `+disconnect` and `+connect` for a server, which was not run against a real remote server in the tests). A reading that finds the same lightmap block with the same bytes is not counted as a second set. A map compiled with a single set gives two identical sets (`union_blue_lock_v2`), reported as such. When the game is not started by Hammer Pro (**Use Garry's Mod if it is already running**) the second reading is not made and only the active set is in the result.
- A texture that cannot be loaded (content not installed on this computer) makes all the texture data that use it share one material object, so the texture info of such a texture that no visible face uses cannot be told apart in memory; `union_blue_lock_v2` has 215 of its 341 textures in that case on the test computer and 72 percent of its texture infos get the right texture data index (100 percent of those of the materials that did load). Install the content and the figure goes to 100 percent.
- Texture data: the reflectivity and size are those of the loaded material and texture objects, so a `$reflectivity` override in a material and a texture that loads at another size differ from the compiled values (3 of 204 and 1 of 204 on `gm_construct`).
- Detail props: the game lump holds an empty detail prop list, because the copy that the detail prop system of the client keeps is not enough to redo the lump. Measured on two test maps compiled with the game tools (312 sprites and 5 dictionary entries, 40 models and 13 entries): the sprites are kept in groups of four (positions bit identical for 293 of 312, within one or two ulp for the other 19, size, colour rounded to 8 bits, pointer to the dictionary entry, which is found back exactly) but not the angle (22 of the 24 angles tested exist nowhere in the process memory) nor the exact lighting colour; the models keep exact origin, angles and colour but neither their model index nor the sway and shape. The compiler records also contain uninitialised padding bytes (187 distinct record tails for 312 sprites), so the lump cannot be redone byte for byte from any source. The detail prop lighting lump is 4 bytes (zero entries) on these maps.
- What the server never sends to the client cannot be recovered: logic, `info_node`, `path_*`, every input and output and every `hammerid` of the entities removed by [Protect your BSP](bsp-protection.md), server only scripts, anything the server keeps to itself. The entities the server does send (weapons, items, npcs, props) come back with the values of the capture, but only while they are in the view of the player. The navigation mesh is a separate `.nav` file that the server never sends either.
- Protected maps: custom materials renamed by the protector keep their scrambled name (the salt is random and not in the map); the material names of a protected map are guessed from the texture reflectivity and the guess can be wrong or missing; the entities the protector removed are gone, except the ones the server networks (see Entities of the client).
- Instances, groups, visgroups and compiler-only brushes are lost, like with any decompile.
- Models and materials are copied from the content on this computer (workshop downloads, addons, server downloads), and the models the game loaded are recovered from its memory; a file that is nowhere is listed as missing in the report.
- The engine can move its structures while they are being read (it finishes loading, or the map is reloaded). The sniffer notices it, because what it finds collapses to nothing, keeps the best complete reading it already had, and looks for the map again from scratch, up to three times. A reading that is worse than the one before never replaces it, so a run either gives the complete map or says in the report what was incomplete.
- A heavy server can need minutes before the engine has built the displacements and overlays; the game answers the automatic disconnect only once it is idle, so the confirmation can take a minute.

## Measured accuracy

The test map is `gm_construct` (2203 brushes, 110 displaced faces, 182 static props, 11 overlays, 28 cubemaps, 607 pakfile files) with a custom material and a custom model added to its pakfile, protected with every option of [Protect your BSP](bsp-protection.md): logic and connections removed, original faces emptied, material names scrambled, watermark, server lock, and then every layout option (shuffled lumps, junk gaps, decoy blocks, scrambled header, shuffled game lumps, pakfile at a random place, reordered tables and world). Each variant was copied to `garrysmod/maps`, started with `map:<name>`, sniffed, and the recovered BSP and VMF were compared with the unprotected map. The result is the same for the protected map and for the ten layout variants (all options together, all layout options, and each option alone):

| What | Recovered |
| --- | --- |
| Solids in the VMF (nodraw, tool, clip, skybox and trigger included), same planes | 2313 of 2313 |
| Brushes and brush models (func_brush and others), same brush sets | 2203 of 2203, 12 of 12 |
| Tool sides (nodraw, skybox, skip, hint, trigger), same material | 4708 of 4708 |
| Brush sides with the real material name (not `hp/xxxxxxxx`) | 12714 of 13798; the other 1084 are the custom material renamed by the protector and 1 side |
| Texture axes of all brush sides | 13796 of 13798 |
| Displacements: positions, normals, distances, triangle tags; now from memory: vertex alphas, allowed vertices | 91 of 91 (110 displaced faces) |
| Static props: model, origin, angles, skin, solidity; now from memory: fade distances, 5 of the 8 flag bits | 182 of 182 (fade distances and the 5 flag bits kept by the engine); the other 3 flag bits (see Limits) came from the map file |
| Overlays, every key; now from memory: render order | 11 of 11 |
| Cubemaps with their size, now read from memory | 28 of 28 |
| Entities that the protector kept, every key and value | 663 of 663 |
| Pakfile | 607 of 607 files, plus the renamed custom files under their `hp/` names |

What stays lost, with the reason: the 839 logic entities (815 `info_node`, `path_*`, `logic_*`) and the connections the protector removed (never sent to the client; the entities a server does send are described in Entities of the client); the real name of the custom material (replaced by a hash with a random salt that is not in the map); 2 sides whose texture axes came from the original faces lump that the protector emptied (the brush side record has other axes, and the decompile of the protected file gives the same result).

The figures above and in the next paragraph were measured with the map file allowed; the lump table in [What the memory gives](#what-the-memory-gives) was measured with no map file. The same sniffer on `union_blue_lock_v2` (a 155 MB workshop map, 8180 brushes, 211 displaced faces, 4967 static props) protected the same way: 8176 of its 8180 brushes and all 812 brush models with the same brush sets, 50624 of 50683 brush sides with the real material name, 50549 of 50683 with the same texture axes, all 211 displacements, all 4967 static props, and 140 MB of lumps taken from the map file. The four brushes that differ are hint and skip brushes that the engine keeps as an axis aligned box: the two slanted faces they have in the file are not in the game at all. The 59 sides whose material differs are sides that no face covers, where the surface name the engine keeps and the brush side of the file disagree; taking the name of the file instead costs more than it gains (50482 correct instead of 50624), because the brush side ranges of that map are damaged, so the name of the game is kept.

## MCP

Every setting and the run itself are reachable through the tools `sniffer_start`, `sniffer_cancel`, `sniffer_status`, `sniffer_log`, `sniffer_result`, `sniffer_get_settings` and `sniffer_set_settings`; the panel opens with the action `bsp_sniffer` (`run_action`). See the [MCP tool reference](../../MCP.md). The settings `game_bits`, `use_map_file` and `read_ldr_lighting` are in `sniffer_get_settings` and `sniffer_set_settings`, and the report returned by `sniffer_result` lists every lump rebuilt from memory with its size, its fidelity (exact, equivalent, partial) and what was not recognised.

## Tips

- Run it once with **Close Garry's Mod when done** off while testing your launch options, then turn it on.
- Keep **Only content that is not in the stock game** on: the result stays small.
- The report file lists what was decoded from the memory with the addresses, the number of map file reads and the optional cross check: attach it to a bug report.

## FAQ

**Does it work with a server I do not own?** Only if you are authorized to test it. The panel asks you to confirm.

**Why does it start the game instead of capturing the network?** The game decodes and loads the map itself; reading what it loaded works whatever way the map reached the client.

**Can it get the server's logic?** No: only what the client receives. That includes the networked entities (weapons, items, npcs, props), not the logic, the nodes, the paths or the inputs and outputs: a search of the whole memory of the game finds no copy of them.

**Is my game or account at risk?** Hammer Pro only reads the memory of the game. On VAC secured servers the game runs with VAC; use it at your own risk and only where the owners allow it.
