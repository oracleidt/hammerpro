# MCP: let AI apps edit your map

Hammer Pro has an MCP server built in. MCP (the Model Context Protocol) is
how AI apps such as Claude (Claude Code and Claude Desktop), Codex and
Gemini CLI use tools. With it, you can ask the AI to look at the map open in
Hammer Pro, add brushes and entities, change materials, check for problems,
save, compile, and take screenshots of the views to check its own work.

Every change the AI makes is one undo step named "MCP: ..." in the Edit
menu, so Ctrl+Z takes it back like any of your own edits.

## Quick start

1. In Hammer Pro, click the **MCP off** pill at the right end of the top
   bar. It turns into **MCP on · port · clients**. The server of that
   window is now on.
2. Click the small arrow next to the pill (or Tools > Integrations > MCP...), then
   **Install in Claude, Codex, Gemini**. Hammer Pro adds itself to every
   app it finds on this computer, in this order: Claude Code, Claude
   Desktop, Codex, Gemini CLI, and checks each one.
3. Restart the AI app (or start a new session) and ask it, for example:
   "Look at my Hammer Pro map and add a 512x512 floor with a light above it."

The pill is off by default in every window. To have it on at start, tick
**Settings > MCP > Start the MCP server when Hammer Pro starts**.

## How it works

```text
AI app (Claude, Codex, Gemini)
    | starts "hammerpro.exe --mcp" and talks MCP on its stdin and stdout
hammerpro --mcp                     the bridge: no window
    | 127.0.0.1, random port, secret token
Hammer Pro window with MCP on       runs the tools on the map it shows
```

- The AI app starts `hammerpro.exe --mcp` itself. That process opens no
  window: it forwards the tool calls to a Hammer Pro window that has MCP on.
- With several windows, the bridge uses the one you focused last, and stays
  with it while it runs. The `list_instances` and `use_instance` tools let
  the AI choose another one; the `HAMMERPRO_INSTANCE` environment variable
  (a process id) names one in the app's configuration.
- When no window has MCP on, the AI still sees the tools, and every tool
  answers that you must open Hammer Pro and switch MCP on in the top bar.
- The bridge speaks the MCP protocol versions 2025-11-25, 2025-06-18,
  2025-03-26 and 2024-11-05 (newline delimited JSON-RPC 2.0 over stdio).

## Security

- **Off by default**, per window. Nothing listens until you click the pill.
- **Local only**: the server listens on `127.0.0.1` (never on the network)
  and refuses any connection that is not from this computer.
- **Secret token**: each time a server starts it makes a random 32 byte
  token. Every connection must send it first or is closed. The token is
  only written in the window's instance record,
  `%LOCALAPPDATA%\HammerPro\mcp\instances\<pid>.json`, in your own profile.
  The record is removed when the server stops or Hammer Pro closes;
  records of crashed windows are ignored and cleaned up.
- **Limits**: messages up to 8 MB, 8 connections at a time per window, a
  timeout on every tool call. The server thread sleeps until a connection
  arrives (no polling): MCP on with no AI connected costs no CPU. A long
  tool call running in the background wakes the window when it ends
  instead of keeping it redrawing meanwhile.
- **File paths**: a tool that takes a file or folder refuses network (UNC,
  `\\server\share`) and device paths (`\\?\`, `\\.\`, `CON`, `NUL`,
  `COM1`...), so a path in a prompt cannot make Windows send your
  credentials to another computer. Relative paths stay inside their folder
  (no `..`); the tools that write next to the map (shader graphs, textures,
  images, sounds, color tables) only accept the map folder and the custom
  texture folders.
- **No programs unless you ask, no arbitrary files**: the tools run no
  command of their own. Files are only `.vmf` maps: `open_map` opens a
  `.vmf`, `save_map` saves the map to its own file or as a new `.vmf` in the
  same folder (replacing another file needs `overwrite: true`). `compile_map`
  compiles with the compiler chosen for the game (Hammer Pro's own by
  default), and starts the game only when the AI explicitly asks for it.
  Creating or changing a compiler that runs other programs
  (`create_compiler`, `set_compiler` with steps) needs `confirm: true`, which
  the AI passes only when you asked for it.
- `run_action` runs any command of the menus, except a few that need
  `confirm: true`, which the AI passes only when you asked for exactly that:
  Exit, switching MCP off, installing MCP in other apps, publishing,
  starting or talking to the game, compiling with the game, editing an
  instance in another window, opening the web browser, and the commands
  that show a file dialog. Automated runs (`--script`) never start the
  game, confirmed or not.
- `set_setting` never changes file paths, folders, programs, command lines,
  the game content folders or the MCP settings: you change those in
  Settings. Key bindings go through `set_keybinding`. The one exception is
  the list of extra entity definition files: `add_fgd` and `remove_fgd`
  take `.fgd` files only and need `confirm: true`; `validate_fgd` reads a
  `.fgd` file without loading it.
- The compile settings go through `set_compile_options` (the same settings
  as the compile window and the toolbar): starting the game after every
  compile (`launch_game: true`) and the folder the BSP is copied to
  (`maps_dir_override`, an existing folder) need `confirm: true`. The
  options of the compiler steps (`bsp_options`, `rad_options`) are checked
  against the compiler's own flags: `-lights` and `-embed` take files of the
  map folder only, and Hammer Pro writes `-game`, `-gmod`, `-threads`, the
  dynamic range and the mode flags itself (from the game configuration,
  `threads`, `lighting` and the modes).
- Baked ambient occlusion is a compile option of the lighting step, off by
  default (the final preset does not add it): `rad_options` `ao: true`,
  `aoradius` (units, default 32, divided by the `sky_camera` scale in the 3D
  skybox), `aoscale` (0 to 1, default 0.5), `aofacesamples` and
  `aopropsamples` (rays, default 32, 16 with `fast`, 64 with `final`) and
  `aodebug` (lightmaps show only the occlusion), in `set_compile_options`
  or `compile_with_options`. The lighting previews never show it.
- `edit_uv_layer` writes layer variants and baked textures in the first
  custom texture folder, and changes a material's own file only when it is
  in a custom texture folder (a backup is kept).
- "Build and save as content" (`start_release`) compiles the map and writes
  its content folder and GMA next to it: a build needs `confirm: true`, an
  analysis (`analyze_only`) writes nothing. Building the cubemaps and the
  navigation mesh in the game during a build (`game_session`) starts Garry's
  Mod: only when you asked, never in automated runs.
- The UI automation tools (`ui_click`, `ui_key`, `ui_type`...) act inside
  the Hammer Pro window only, like your mouse and keyboard there; positions
  outside the window are refused.

Tool calls run on the editor's own thread, between two frames, like a click
of yours.

## Install

The **Install in Claude, Codex, Gemini** button (Tools > Install MCP in
Claude, Codex and Gemini) and the per app buttons of the MCP window do the
following. Each app line shows its state: not installed on this computer,
installed but not configured, installed and configured, configured for
another copy of Hammer Pro (click Update), or the error. The apps' own
programs (the `claude` command) only run when you click Install, Verify or
Remove.

| App | What is changed |
|---|---|
| Claude Code | `claude mcp add --scope user hammer-pro -- "<hammerpro.exe>" --mcp` (checked with `claude mcp get hammer-pro`). `~/.claude.json` is never edited directly: running Claude Code sessions rewrite it. |
| Claude Desktop | `mcpServers` of `%APPDATA%\Claude\claude_desktop_config.json` (or the Microsoft Store copy under `%LOCALAPPDATA%\Packages\Claude_*`) |
| Codex | `[mcp_servers.hammer-pro]` of `~/.codex/config.toml` (or `%CODEX_HOME%`) |
| Gemini CLI | `mcpServers` of `~/.gemini/settings.json` |

Before the first change, each file is copied to `<file>.hammerpro.bak`.
Files are written through a temporary file, everything else in them is kept
(other servers, comments in the TOML file), and the result is read back to
verify it. A JSON file with comments is not touched: add the entry by hand.

Moved Hammer Pro to another folder? Open the MCP window: the apps show
"configured for another copy"; click Update (or Install in Claude, Codex,
Gemini).

## Manual setup

The MCP window shows these snippets with the real path of your
`hammerpro.exe` and a Copy button (Manual setup).

Claude Code:

```bash
claude mcp add --scope user hammer-pro -- "C:\Program Files\Hammer Pro\hammerpro.exe" --mcp
```

Claude Desktop (`claude_desktop_config.json`) and Gemini CLI
(`~/.gemini/settings.json`):

```json
{
  "mcpServers": {
    "hammer-pro": {
      "command": "C:\\Program Files\\Hammer Pro\\hammerpro.exe",
      "args": ["--mcp"]
    }
  }
}
```

Codex (`~/.codex/config.toml`):

```toml
[mcp_servers.hammer-pro]
command = 'C:\Program Files\Hammer Pro\hammerpro.exe'
args = ["--mcp"]
```

Any other MCP app: a stdio server with the command `hammerpro.exe` and the
argument `--mcp`.

## Place things precisely

Bounding boxes and origins lie: a couch's origin is not at its feet, a
rotated prop's box is bigger than the prop, a lamp's box says nothing about
where its wall plate is. The placement tools measure the real geometry: the
`.mdl` mesh after angles, `modelscale` and body groups (and the `.phy`
collision mesh), brush planes, displaced surfaces, overlay quads, instance
contents and groups. They work the same for every kind of object, as the
thing being placed and as the surface or neighbour.

1. **Measure**: `get_object_shape` (any object, or a model path before it is
   placed) gives exact bounds, `bottom_z`, the footprint polygon and its
   smallest rectangle, the contact patch, `origin_above_bottom` (how high the
   origin sits above the lowest point), the oriented box, slices and, with
   `detail` full, a top height map. `get_model_info` adds the same `shape`
   numbers to a model's information. `render_shape` draws the object, a
   model or a whole box from several axes with sizes, the origin and the
   lowest point.
2. **Place**: `place_object` moves objects or creates a prop so that its
   real mesh touches: `drop` (falls until it touches, sunk objects are lifted
   out first), `on` (on top of a target), `against` (flush with a wall,
   `facing` away turns a model's front away from it), `next_to` (beside a
   target, flush, then on the floor), `at`. `drop_to_surface` drops several
   objects at once, lowest first so stacks settle. With `fit` supports,
   `place_object` tilts an object until its lowest points (wheels, legs) all
   touch when they can, and says why when they cannot (a crest under the
   body). The editor's own Move to floor, Move to ceiling and Physics
   placement commands use the same engine.
3. **Verify**: `check_placement` tells for each object whether it rests,
   floats (`gap_below`), is sunk, only touches a wall (attached), and which
   objects it interpenetrates with the depth and the push that frees it.
   `find_floating_objects` scans the map or a box and can fix what it finds
   in one undo step. `trace_ray` and `query_box` (with `exact`) also use the
   real meshes.

Numbers are rounded to 0.01 unit, Source units (1 unit = 1 inch), Z up.
Placements stop at most 0.01 unit short of the contact, never inside.

## Paint foliage and grass

- `paint_foliage` paints props from a palette along stroke points (one brush dab per point, traced down onto displacements, brushes and props), with density per area, spacing, scale, yaw, alignment, slope and height limits, overlap avoided on the real model footprints and props dropped onto the real surface. The props join the visgroup `Foliage: <palette>`; `erase_foliage` removes them under the brush. Each call is one undo step, like a stroke of the Foliage tool.
- Grass of `%detailtype` materials: `list_detail_types` reads `detail.vbsp`, `preview_detail_props` computes what the compile will emit (the same placement as the compiler), `paint_displacement` with mode `alpha` paints where the groups grow, and `set_face_detail_type` gives faces their own type or `none`.

## Tools

Coordinates are Source units (Z up). Ids are the VMF ids; when an entity and
a solid share an id, `ids` names the entity and `solid_ids` the solid.

Displacement tools without `faces`, `ids` or `solid_ids` work on the displacements selected last: the
selected displacement faces, or every displacement of the selected solids when objects were selected after
them (a selected group of displacements is therefore handled as a whole).

Redundant brushwork: `check_problems` with `category` `redundant` (or `get_problems` with a code among
`duplicate_brush`, `contained_brush`, `duplicate_entity`) lists brushes that are exact copies of another
brush of the same entity, brushes fully inside another solid brush of the same entity and entities stacked on
an identical one. `find_duplicate_brushes` lists each copy with the object it duplicates and can `select` or
`delete` the copies (one undo step); `fix_problems` with those codes deletes them too. The live warning when
a new object is an exact copy is the setting `health.warn_duplicates` (`set_setting`).

func_detail: `make_func_detail` turns world brushes (`ids` / `solid_ids` or the selection) into func_detail in one
undo step, like the Make func_detail action (`Ctrl+Alt+D`): `split` `selection` (one entity) or `cluster` (one per
group of touching brushes), groups, visgroups and textures kept, and a leak flood first finds the brushes that seal
the map (`sealing`: `skip` converts the others, `refuse` converts nothing, `allow` skips the check).
`select_detail_candidates` only selects the world brushes the optimization advisor would turn into func_detail
(`max_size`, `kinds`, `within`, `within_selection`). `run_action` `convert_to_detail`, `select_detail_candidates` and
`toggle_detail_tint`, and `set_setting` `brush.detail.*` (`split`, `check_sealing`, `tint` and the candidate filters)
reach the same features; `set_tool_options` `create_as` `func_detail` makes the creation tools build detail directly.

Cubemaps: `analyze_cubemaps` reports the rooms with reflective (`$envmap env_cubemap`) materials, which
`env_cubemap` each face takes (sides first, then the nearest one in front, like VBSP), faces taking the cubemap of
another room or one behind a wall, and misplaced, oversized or redundant cubemaps. `suggest_cubemaps` gives
cubemaps at eye height and `sides` fixes, and with `apply` places them in one undo step (`size` for the new
ones). `show_cubemap_assignment` colours the faces by their cubemap in the views (off by default, look with
`screenshot_view`). `run_action` `show_cubemaps` opens the Cubemaps window and `toggle_cubemap_assignment` toggles
the view. The same findings are the `cubemaps` topic of `optimize_map`, which never edits cubemaps.

Smooth 3D camera: the setting `workflow.camera_smoothing` (`set_setting`, on by default) gives the fly camera its
acceleration and deceleration (`workflow.fly_response` seconds) and makes following a Team Mapping teammate glide;
off, the camera starts and stops the frame a movement key is pressed or released and jumps to a followed teammate.
`run_action` `toggle_camera_smoothing` toggles it like the View menu and the 3D view header menu. Mouse look, the
wheel, orbit and trackpad gestures are never smoothed; `set_camera` always places the camera at once.

Vertices on top of each other: by default (setting `vertex.merge_prompt` = `off`) vertices that a vertex tool move
stacks merge silently, as in earlier versions. With `ask` (`set_setting`), a move (drag in a 2D or 3D view, arrow keys,
snap, align, scale, edge loop rotate or slide) that ends with vertices of a solid on top of each other asks "These
vertices are on top of each other. Merge them?" like Hammer (Yes merges in the same undo step as the move, No undoes
the move); `always` merges without asking and `never` undoes such moves. `move_brush_vertices` never shows the
question: its `merge` argument (`off`, the default and the behaviour of earlier versions, `yes`, `no` or `ask`) gives
the answer, and its result tells how many vertices the solid lost (`merged`), whether the move was `applied` and,
when it was not, the `stacked` vertices.

## Seeing and driving the interface

Besides the semantic tools, the AI can reach everything you can:

- `get_capabilities` lists every tool by category with an example call
  (start here), or one tool with its schema.
- `list_actions` and `run_action` expose every command of the menus,
  toolbars and shortcuts automatically, with its enabled and checked state
  and its `menu_path` (where it sits in the menu bar, such as
  `File > Import` or `Tools > Arrange`).
- `get_settings` and `set_setting` read and change any setting by path
  (`view.fov_deg`, `ui.theme`), validated like the Settings window;
  `list_keybindings` and `set_keybinding` the shortcuts.
- The toolbar and the tool palette are settings too:
  `workflow.toolbar_rows` (1 or 2: wrap on a second row when the window is
  narrow), `workflow.toolbar_order` (group ids `file`, `edit`, `grid`,
  `groups`, `hide`, `cordon`, `display`, `show`, `render`; Compile always
  stays at the right end), `workflow.toolbar_hidden` (group ids, `compile`,
  and button ids: the action id of the button, or `grid_size`,
  `render_mode`, `props_2d`, `primitive_stats`; unknown ids are refused) and
  `workflow.tool_palette_columns` (1 or 2). The actions
  `toolbar_two_rows`, `tool_palette_two_columns` and `reset_toolbar`
  (`run_action`) do the same as the right-click menus. `describe_ui` reports
  `toolbar_rows` and `tool_palette_columns` with the panels, and names the
  toolbar buttons after their action.
- Propper: `run_action brushes_to_prop` opens the creation window for the
  selected brushes/displacements. Review its integrated 3D preview, model/export
  paths, collision generation/manual pieces, `$illumposition`, `$bbox`,
  `$surfaceprop`, `$staticprop` and `$cdmaterials`, then click Create prop.
  Collision offers No collision, Box and Precise, with advanced hull/manual
  editing. Existing VertexLitGeneric material and texture paths are reused by
  default; disable their reuse checkbox to copy them into `$cdmaterials` too.
  Defaults include `lab.propper_physics`, `lab.propper_static`,
  `lab.propper_collision` and `lab.propper_mass`; physics forces collision on and
  static off. The resulting entity is `prop_static`, `prop_dynamic` or
  `prop_physics`. `prop_to_brushes` goes back. The levels of detail of every model
  Hammer Pro makes (Propper and the FBX, OBJ, glTF import) are the settings
  `lab.model_lod.enabled`, `lab.model_lod.levels` (3 to 6, default 4) and
  `lab.model_lod.reduction` (0.2 to 0.9, default 0.5); `run_action
  propper_options` opens their window. The model import also writes the
  normal map, phong, self illumination and texture tiling of the file into
  the VMTs while the setting `lab.model_keep_params` is on (the default;
  `run_action import_model` opens the import window, which lists the
  materials; the console reports per material what was converted and what
  was ignored).
- `get_views`, `set_view_layout`, `set_render_mode`, `zoom_2d`, `pan_2d`
  and `set_camera` arrange the views (render modes, the baked lighting
  preview, the 2D displacement mesh or outline of each view). The water
  preview (water drawn like in game in the textured 3D modes) is the
  setting `render.water_preview` and the action `toggle_water_preview`.
  The fog of the `fog_volume` brushes (from the `env_fog_controller` of
  their Fog Name, also applied in the player view while the eyes are
  inside) is `render.fog_volume_preview` (`toggle_fog_volumes`), their
  brush material `render.fog_volume_texture`
  (`toggle_fog_volume_texture`); the fish of `func_fish_pool` are
  `render.fish_preview` (`toggle_fish_preview`) and swim with
  `render.fish_swim` (`toggle_fish_swim`).
  The relief of the normal maps (`$bumpmap`, `$bumpmap2` of blends,
  `$ssbump`, on brushes, displacements and props; the compiled bumped
  lightmaps in the player view) is the setting `render.normal_maps` (on by
  default).
- The baked lighting preview runs in a warm lighting process: light edits
  relight only the changed lights and their bounced light, usually in a
  fraction of a second (`get_lighting_status` `relight` gives the last update,
  its timings and the memory of the process). `run_action
  solo_selected_lights`, `mute_selected_lights` and `unmute_all_lights` (or
  `set_lighting_options` `solo`, `mute`, `unmute`, `unmute_all`) leave lights
  out of the preview; `run_action measure_light_costs` (or
  `get_lighting_status` with `costs: true`) measures the faces and luxels each
  light reaches (`light_costs`). The setting `lighting.visible_first` (on by
  default) bakes the area around the camera first on maps of 6000 solids and
  more, then the whole map. The setting `lighting.prepare` (on by default)
  compiles and lights the whole map at low priority in the background once
  the map is open and edits pause, so `set_render_mode` `baked` shows it at
  once (`get_lighting_status` `prepared`: `preparing`, `ready`, `jobs`,
  `seconds`; `streamed_faces` counts the faces of the first bake already shown
  with their light, nearest the camera first). Lights dragged with the
  selection tool are relit during the drag each time the mouse rests for
  `lighting.drag_pause_ms` (120 by default, 0: continuously), and a light
  edit stops a running refined pass, which starts again after it. The
  bakes never compete with the editor and the other programs: they run below
  normal priority (`lighting.priority`: `Idle`, `BelowNormal` by default,
  `Normal`; the background preparation and the props always at `Idle`) on
  every core but a quarter, with at least two cores left free
  (`lighting.threads`, 0 by default, capped to every core but two). Turning
  the baked mode off while a bake runs stops it, and the lighting of the props
  with it; both start again when the mode comes back. `lighting.pause_minimized` (on) and
  `lighting.pause_unfocused` (off) stop the running bake and start no new one
  while the window is minimized or another window is active
  (`get_lighting_status` `paused`; `threads` and `priority` tell what the
  next bake uses). `lighting.upload_mb_per_frame` (4) caps the lightmap data
  sent to the graphics card in one frame. Moving the camera or changing the
  selection never starts a bake.
- The live map checks (`health.live_checks`, the leak check and the placement
  check of floating, sunk and overlapping props) wait until the edits pause for
  `health.check_delay_ms` (1500 by default, never while dragging), run at the
  lowest priority on a third of the cores (at least two cores left free), check
  again only the props near an edit, and stop while the window is minimized
  (`health.pause_minimized`, on by default).
- `get_tool_options` and `set_tool_options` read and change the options of
  the editing tools like their panels (the block tool's primitives, arch
  and its preview window; the displacement brush: axis with the view
  direction, intensity, live sewing, line of sight, sculpting...), and
  `stroke_displacement` paints with that brush like a drag in the 3D view
  (`boost` smooths 4 times stronger, like `Ctrl`). `sample_displacement_height`
  samples the surface under a point like a right click of the displacement
  tool (into `target_height`, the slope points or `alpha_value`) and
  `paint_displacement_slope` paints a ramp between two points (`start`,
  `end`) with the Slope brush; the options `smooth_boost`,
  `height_reference`, `slope_brush_start`, `slope_brush_end` and
  `slope_brush_strength` drive them.
  The polygon, entity, decal and overlay tools have their options too
  (texture scale, create as, next entity class, model, skin, snapping), and
  the physics simulator runs on the selection with `simulate` (seconds of
  physics at once, then paused), `keep` (one undo step) and `reset`.
- `get_compile_options` and `set_compile_options` read and change every
  compile setting and every option of the compiler (`get_compilers` lists
  the flags with what they do); `list_compilers`, `get_compiler`,
  `get_compiler_flags`, `create_compiler`, `set_compiler`,
  `delete_compiler`, `select_compiler` and `reset_compilers` manage the
  other compilers (Valve's tools found next to the game, your own) with every
  option of vbsp, vvis and vrad as structured fields; `get_compile_log` explains the problems the
  compile reports, from this window or from `<map>.log`; `get_compile_stats`
  gives the statistics of that log to optimize the map (engine limits like
  vbspinfo, brushes, materials, areas, the clusters that see the most, the
  faces with the most luxels, stage times) and hints in plain words with
  the brush, side or place they are about.
- `screenshot_window` returns a PNG of the whole window (optionally a
  region, downscaled), `screenshot_view` one view rendered offscreen.
- `describe_ui` tells what is on screen: open maps, views and their
  rectangles, panels, open windows and dialogs with their texts and their
  controls (with the point to click), open menus, the focused widget, the
  status bar, notifications and the end of the console. The buttons of the
  tool palette (the strip along the left edge) are named after their tool
  ("Block", "Clip"...). The headers of collapsible sections ("Filters and
  display" of the texture browser, the option menus of the compile window...)
  are controls of role "section": click one to open or close it.
- `ui_move`, `ui_click`, `ui_double_click`, `ui_drag`, `ui_scroll`,
  `ui_key` and `ui_type` send mouse and keyboard input like the user, at
  window points, at fractions of a view, or at world points of a view
  (`{"view": "top", "world": [0, 0, 0]}`); `wait_frames` lets the interface
  settle. The input goes through the same path as the `--script` engine.
- `ui_scroll` with `trackpad: true` sends a two finger trackpad scroll
  (`dx`, `dy` in points) and with `pinch` a trackpad pinch (a zoom factor),
  so the trackpad gestures can be tested: with `input.trackpad_mode` set to
  `"On"` (or `"Auto"` after a first trackpad event) a scroll pans a 2D view
  and orbits or moves the 3D camera (`input.trackpad_scroll_3d`), a pinch
  zooms. `set_setting` changes `input.trackpad_mode`,
  `input.trackpad_scroll_3d` and the speeds `input.trackpad_pan_speed`,
  `input.trackpad_zoom_speed` and `input.trackpad_orbit_speed` (0.25 to 4).
- `ui_drag` with `hold` keeps the button down at `to` for that many frames
  before releasing. With `workflow.drag_autopan` on (`set_setting`, off by
  default, **Settings > Viewports > Scroll the 2D view when dragging to its
  edge**), a left drag held within 16 points of the edge of a 2D view or past
  it scrolls that view toward the cursor, faster the farther the cursor goes,
  and what is dragged keeps following the cursor in world space (like Hammer).
  `get_views` shows the moved 2D camera.

## For developers

- `crates/hp-mcp`: protocol (`protocol.rs`), tool list and schemas
  (`tools.rs`), instance records (`registry.rs`), the window server
  (`server.rs`), the bridge (`bridge.rs`), the installer (`install.rs`).
- `crates/hammerpro/src/dispatch/mcp.rs`: server life, request dispatch,
  compile and open; `dispatch/mcp/tools.rs`: the core tools and the
  registry (`DOMAINS`: one `tools_<area>.rs` per area, each with its
  category, tool descriptions and `run`); `dispatch/mcp/window.rs`: the MCP
  window.
- Generic tools: `tools_actions.rs` (every action), `tools_settings.rs`,
  `tools_views.rs`, `tools_ui.rs` (UI automation and vision),
  `tools_help.rs` (`get_capabilities` and the tool list of this page);
  `automation.rs` answers the calls that need frames (input injected from
  `raw_input_hook`, screenshots encoded on a worker thread) and
  `describe.rs` reads egui's AccessKit tree for `describe_ui`.
- The tool list above is generated: after adding or changing a tool, run
  `HP_UPDATE_MCP_DOCS=1 cargo test -p hammerpro docs_list_every_tool`.
  `harness.rs` calls every tool through the protocol with its example and
  with invalid arguments.
- Tool options: `tools_toolopts.rs` uses the tools' own
  `Tool::option_values` and `Tool::set_option` (the `tool_option` command
  of `--script` too) and `Tool::scripted_stroke` (`stroke_displacement`);
  a tool with options lists them there. The UV layers use
  `hp_ui_textures::uv_layers::{mcp_layers, mcp_apply_layer}`, the same
  model and writes as the UV editor.
- `crates/hp-app/src/{actions,settings,runtime}/mcp.rs`,
  `crates/hp-ui-shell/src/{status,settings_dialog}/mcp.rs` and
  `toolbar::mcp_pill`: actions, settings, shared state and UI.
- `HAMMERPRO_MCP_DIR` moves the instance records (tests and automated
  checks). `scripts/mcp_check.py` drives a real Hammer Pro through the
  bridge.
